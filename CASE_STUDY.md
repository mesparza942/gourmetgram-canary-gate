# Evaluation dataset and case study

**Question.** Can runtime evaluation flag GourmetGram releases that degrade service, and how much time and computing capacity does the gate add before promotion? The proposed study measures latency, failures and request-handling capacity on the reproduced Chameleon deployment. Model prediction quality is outside the endpoint performance outcome.

## Data to collect

Food-11 is the input workload. The new research dataset is the evidence recorded while requests exercise the two deployments. The [Food-11 publication](https://doi.org/10.1145/2986035.2986039) describes the source images. The [Chameleon evaluation example](https://teaching-on-testbeds.github.io/eval-online-chi/) illustrates selecting images from its splits.

| Record | What it contains | Purpose |
|---|---|---|
| Image manifest | Dataset release, split, seed, image ID and SHA-256, class ID, relative path and byte size | Reproduce the payload mix and check that the pilot and final samples are disjoint |
| Request log | Trial folder and environment, scheduled slot, image ID, planned and actual start offsets, duration, outcome and HTTP status | Recompute the metrics and identify missing or late sends |
| Trial metadata and decision | Phase, paired workloads, application image and model versions, deployment configuration, offered rate, scenario assignment, measurement boundaries, policy version, summaries and decision reasons | Trace each decision to the exact deployment, workload and policy |
| Cost and baseline record | Gate start/end time, resource samples, node placement, background jobs and the operator's decision and elapsed time if a manual baseline is run | Estimate overhead and explain variation |

Use 20 images per class as an initial balanced workload, with validation images for the pilot and evaluation images for final trials. Record the source archive revision or hash; confirm the license for its release before distributing image files. After generating the manifests, check image decoding and record class and byte-size distributions. Compare the selected sample against its source split and document major gaps. This is a controlled test workload with class coverage, so make generalization claims only about the tested payloads and loads.

Keep immutable request logs and manifests alongside the trial index, with keys linking model versions and the final decision. Store the scenario assignment separately from the validator's input. The report should publish or attach the sanitized measurement dataset, data dictionary, analysis instructions and commit hash, permitting a reader to recompute the reported values. Use metadata alone to identify inputs in the logs.

## Trial procedure

1. **Preflight.** Verify the current cluster and reproduce baseline serving if needed. Record the resolved image IDs, application/model versions, CPU and memory limits, node placement and background workload. Run a low-rate smoke test on the isolated environment endpoints to verify the image upload and response contract. Use a dedicated copy or isolated candidate path for deliberately altered behavior.
2. **Pilot.** Use only the pilot images. Start with identical serving versions and resources on both sides. Check normal variation, client queueing, start-rate accuracy and repeatability of the injected delay and error profiles. Pick two sustainable offered rates and predefine what constitutes acceptable service for the study. Validate the initial policy and freeze the policy, power or precision target, scenario parameters, seeds and analysis before recording final trials.
3. **Pair.** Warm up for 30 seconds. For the planned 120-second measurement, start the same ordered images on both endpoints at matching paced offsets. Cycle the same seeded shuffle of the manifest when more slots than input images are needed. Collect one outcome per slot with a bounded timeout and no retries. Use concurrent measurements with equivalent service resources and sufficient generator headroom. Record placements and repeat an identical-version control to reveal interference. If contention requires staggered measurements, pilot a shorter window that fits the five-minute gate deadline and still provides at least 200 responses per environment. Record that protocol change before the final study.
4. **Vary conditions.** Use healthy, added-delay and injected-error families at each load. Start with 10 paired repeats per family/load, for 60 pairs, then revise this number on pilot evidence. Preassign and randomize order within workload blocks, and spread each family across time. Include mild and larger injected effects in each fault family and report their severity separately. Preserve the existing candidate workflow and a fixed Production reference while evaluating decisions. Exercise a promotion-enabled integration case separately.
5. **Verify pacing.** Record intended starts, actual starts, late starts and generator misses. Keep the paired requests separate from ordinary gateway traffic. The current Python collector schedules starts independent of request completions and records a missed start if its in-flight capacity is full. Confirm the schedule on the cluster while response times and load rise. If using Locust for a later run, validate the same timing and offered-rate conditions. [Locust documentation](https://docs.locust.io/en/stable/writing-a-locustfile.html#wait-time)

## Baseline, labels and analysis

- **Original baseline.** The teaching pipeline runs Staging tests and then requires operator observation and a manual promotion action from Canary. For a direct comparison, use a predefined observation checklist and time budget based on that workflow. A reviewer records approve, reject or defer on each comparable case while blinded to the injected condition and to the gate result. Record the evidence the reviewer actually had. If a faithful manual run is unavailable, limit the conclusions to fault detection and gate cost and report the comparison with the operator workflow as qualitative. [Original promotion procedure](https://teaching-on-testbeds.github.io/mlops-chi/#promotion-to-production)
- **Independent assignment.** Assign conditions from the scenario configuration before observing gate decisions. Use a separate verification, such as the injection log and a calibrated reference check, to confirm the fault operated. Predefine severity and service objectives separately from the gate thresholds. Report mild faults as a sensitivity analysis when their user impact is ambiguous. The rate of PASS on known faults describes detection in this case study. Comparing that rate to manual decisions requires the manual baseline above.
- **Decision behavior.** Report denominators and counts of PASS, FAIL and HOLD by scenario and load. Report degraded candidates passed and healthy candidates failed or held. Keep HOLD reasons visible. Use the paired trial as the experimental unit. Show paired metric differences and variability, with uncertainty intervals where replication supports them. If all 60 pairs are retained, present them as an initial case study and note that severity subgroups will have few repetitions.
- **Overhead.** Time the full gate from evaluation start through the recorded decision. Capture CPU-core-seconds and peak memory for the evaluator and generator, with the same sampling approach across trials. Compare instrumentation enabled versus disabled at matched load, using the same low-cost client timing on both sides to estimate added p95 latency. The initial 5% target applies to added p95 latency. Tune the five-minute deadline and resource budget on the pilot and report any deadline misses.
- **Interpretation.** With a 5% offered-rate tolerance and a 2% failure-rate ceiling, the 90% successful-request-rate floor cannot independently change a PASS under the prototype's current metric definitions. Retain it for continuity and report it as a cross-check. If the study needs a separate capacity signal, pilot a completion-by-deadline or higher-load measure and explain any policy change before the final trials.

The [measured local pilot](PILOT.md) exercises the collector and gate with both an identical-version control and a delayed candidate. It records 840 real prediction requests using 22 Food-11 images.
